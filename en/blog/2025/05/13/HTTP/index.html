TCP​

ISN(Initial Sequence Number): 初始序号. MSL(Maximum Segment Lifetime): 一个包在网络中滞留的时间.

ISN生成器: TCP协议的要求是,实现一个大约每4微秒加1的32bit计数器(时钟),在每次创建一个新连接时使用这个计数器的值作为ISN.

在rfc1948中提出了针对seq num进行猜测攻击的问题. 在rfc6528中提出了新的seq num生成算法用于替换RFC793中的方案.

一般不用0作为ISN起始号,这是为了安全考虑. 因为如果在3次握手中,攻击者在发起连接的一方未收到ACK时而率先发送自己的ISN,而抢先和对方建立连接,这时3次握手成了非法入侵者的机会.

TIME-WAIT: TCP协议要求在断开连接时,TIME-WAIT状态需要保留2 MSL的时间才能转成CLOSED. 因为需要保证上一次连接的所有重复包都会消失.

TCP握手三个步骤​

A: 我的数据从x开始编号 (SYN) B: 我的从y开始编号 (SYN-ACK) A: 开始通话 (ACK)

三次握手的目的是为了防止已失效的连接请求报文段突然又传送到了服务端，因而产生错误. 具体表现为同步连接双方的序列号和确认号并交换 TCP窗口大小信息.

需要确认的原因是需要杜绝建立旧的连接

四次挥手是因为A要断开连接,在过程中虽然A不再发送数据给B,但是B还是可以发送消息给A,所以不能一次性断开所有联系

第四行介绍:

  • 数据偏移量: 4字节的倍数,最小是0101(5),表示数据从第 20 个字节开始(大部分情况)
  • 控制位(CTL): 一共6个,ACK、SYN、FIN就不介绍了.
    • RST 是Reset,遇到异常情况时通知对方重置连接(我们敬爱的防火墙很爱用它).
    • URG 表示这个报文很重要,应该优先传送、接收方应该及时给上层应用.
    • PSH 表示这个报文不应该被缓存、应当立即被发送出去. 在交互式应用中比较常用,如ssh,用户每按下一个键都应该及时发出去.注意和Nagle算法可能会有一些冲突.

关键点: 协商一个序号的过程需要一个来回(告知+确认),理论上一次连接总共需要2个来回(4次),互相确认了双方的初始序号(ISN,Initial Sequence Number),才能真正开始通信.

由于第二个来回的"告知"可以和前一次的"确认"合并在同一个报文里(下面有实现的介绍),因此最终只需要3次握手,就可以建立起一个tcp连接.

第二个来回的介绍​

SYN和ACK合并的报文生成过程(联系上面的协议): Sequence Number填入从ISN生成器中获取的值. Acknowledgement Number填入[发送方的序号+1]. 将控制位中的ACK位、SYN位都置1.

Reliability(可靠性)的具体定义是: TCP协议必须能够应对网络通信系统中损坏、丢失、重复或者乱序发送的数据.

其它​

  • 一个包在网络中滞留的时间通常是有限的,这个时间我们称之为MSL(Maximum Segment Lifetime),工程实践中一般认为不会超过2分钟.
  • 握手的目的是双方协商初始序列号ISN.
  • 序列号是为了解决ACK分组受损或丢失而超时重发哪些分组,以及分组排序(选择重传差错恢复策略).
  • 通信可靠性保证: 序列号、检验和、ACK分组、重传机制.

HTTP2​

文章: 知乎、HTTP简史、中文资料、HTTP/1.1 vs HTTP/2: What's the Difference、讲清了HTTP1.1和HTTP2的基于文本传输的基于帧传输到底哪不同

HTTP1.1的几个问题​

  • 单个 TCP 连接在一个时刻只能处理一个请求
  • head of line blocking: 在导致多健康请求可能会别单个不健康请求阻塞.
  • 连接无法复用: 在HTTP1.0协议中可以携带请求头Connection:Keep-Alive使连接在一定时间内复用. 在HTTP1.1中默认携带.

HTTP2适用场景​

它对PC端浏览器的体验帮助很大,因为大部分的请求在集中在一小段时间以内. 但对移动app来说,成效不大,app端的请求比较分散且时间跨度相对较大,所以app一般从'应用层'使用其它解决方案.

HTTP2以前的"服务端消息推送"方案​

  • 方案一: 基于tcp的长链接

    基于tcp的socket编程来自己定制协议,比如google的gRPC.

  • 方案二: http long-polling

    客户端在初始时就发送一个polling请求,服务端会在需要返回的时候返回. 连接会一直被保持,一旦结束马上又会发一个新的请求.

  • 方案三: http streaming

    大致与polling相同,也是单向的. 处理和polling有相同的难点之外(可靠性、服务器压力)还有几个缺点:

    1. 有些代理服务器会等待服务器的response结束之后才会将结果推送到请求客户端.对于streaming这种永远不会结束的方式来说, 客户端就会一直处于等待response的过程中.
    2. 业务数据无法按照请求来做分割,所以客户端没收到一块数据都需要自己做协议解析,也就是说要做自己的协议定制.

  • 方案四: web socket

    基于tcp协议,双向数据通道.

  • HTTP1.1针对Head of line blocking问题的解决方法(pipelining):

    现在,多个请求时无需阻塞等待响应,几乎是同一时间将request发向了服务器,解决了发送请求时的阻塞问题.

这几个"服务端推送"方案存在的问题:

  1. pipelining只能适用于http1.1,一般来说,支持http1.1的server都要求支持pipelining
  2. 只有幂等的请求(GET,HEAD)能使用pipelining,非幂等请求比如POST不能使用,因为请求之间可能会存在先后依赖关系
  3. "head of line blocking"并没有完全得到解决,server的response还是要求依次返回,遵循FIFO(first in first out)原则.也就是说如果请求1的response没有回来,那么2,3,4,5的response也不会被送回来
  4. 绝大部分的http代理服务器不支持pipelining.

特殊场景的其它方法:

  • Spriting(图片合并)
  • Inlining(内容内嵌): 和Spriting思路类似,用Base64编码来压缩请求次数.
  • Domain Sharding(域名分片): 针对请求次数限制是根据域名来组判断的,所以可以分成多个域名来扩充请求次数限制. 一般用于PC端的图片等不需要Cookie、的请求.

SPDY(SPeeDY)​

SPDY的诞生和表现说明了两件事情: 1: 在现有互联网设施基础和http协议广泛使用的前提下,是可以通过修改协议层来优化http1.x的. 2: 是针对http1.x的修改确实效果明显而且业界反馈很好.正是这两点让IETF(Internet Enginerring Task Force)开始正式考虑制定HTTP2.0的计划,

最后决定以SPDY/3为蓝图起草HTTP2.0,SPDY的部分设计人员也被邀请参与了HTTP2.0的设计

  1. 赫夫曼编码,压缩数据
  2. 缓存相同请求头信息,可以在HTTP2资料汇总开控制台看到缓存.

实现细节​

目前Header头静态表中有61个预定义Header头字段. 协议中所有写成(N+)的数字,例如Index (4+)、Name Length (7+),都需要按照'4.'所介绍的规则来计算整数值.

  1. 整个头部键值对都在字典中: 取一个字节,最左位固定为1,后七位存放键值在静态或动态字典中的索引.

  2. 头部名称在字典中,更新动态字典: 组成格式: '头部名称'(一个字节)+'值长度'(一个字节)+'值'(N个字节). '头部名称'左两位固定为'01',之后六位存放头部名称在静态或动态字典中的索引. '值长度'第一个位表示是否使用了"赫夫曼编码",剩余表示值长度. 紧跟着的后N位表示具体值.

  3. 头部名称不在字典中,更新动态字典: 组成格式: '头部名称'(一个字节) + '头部长度(一个字节)' + '头值(N个字节)' + '值长度'(一个字节) + '值'(N个字节). 跟2类似,只不过'头部名称'不在字典中.

  4. 头部名称在字典中,不允许更新动态字典: 组成格式: '头部名称'(一个字节)+'值长度'(一个字节)+'值'(N个字节). 跟2类似,不同在于它们不允许被添加到动态字典中,且'头部名称'计算规则不同.'头部名称'第一个字节左四位固定为0001,剩下四位放索引. 计算规则为:

    # 后四位只能代表小于、等于[2^N-1=15]的整数,标记为I,所以得重新制定计算规则.
    if I < 2 ^ N - 1, return I         # I 小于 2 ^ N - 1 时,直接返回
    else
        M = 0
        repeat
            B = next octet             # 让 B 等于下一个八位
            I = I + (B & 127) * 2 ^ M  # I = I + (B 低七位 * 2 ^ M)
            M = M + 7
        while B & 128 == 128           # B 最高位 = 1 时继续,否则返回 I
        return I

    比如一个名称字节为00011111,则需要继续往后读一个字节. 这里假设为00010001(这里因为最高位为0,就不需要继续往后读了),所以索引对应名称为cookie(1111+00010001=15+17=32).

  5. 头部名称不在字典中,不允许更新动态字典: 和4类似,不同在第一个字节固定为00010000,其它结构什么的都一样. 头部键值对也不允许被添加到动态字典中,只能用哈夫曼编码减少体积.

NPN(Next Protocol Negotiation)和ALPN(Application Layer Protocol Negotiation)之间的区别​

他们的区别在于谁来决定通信协议. 在ALPN的描述中,是让客户端先发送一个协议优先级列表给服务器,由服务器最终选择一个合适的.而NPN则正好相反,客户端有着最终的决定权.

HTTP2的几个概念(来自Jerry Qu)

  • 帧(Frame): HTTP/2 数据通信的最小单位.帧用来承载特定类型的数据,如HTTP首部、负荷;或者用来实现特定功能,例如打开、关闭流.每个帧都包含帧首部,其中会标识出当前帧所属的流;
  • 消息(Message): 指 HTTP/2 中逻辑上的 HTTP 消息.例如请求和响应等,消息由一个或多个帧组成;
  • 流(Stream): 存在于连接中的一个虚拟通道.流可以承载双向消息,每个流都有一个唯一的整数 ID;
  • 连接(Connection): 与 HTTP/1 相同,都是指对应的TCP连接;

抓包发现: 在一次响应中如果需要分多'帧'来返回数据(DATA)的话,在流(Stream)的数据结构中会有相同ID,还会有flags: 0x01来表示为结尾流,表示当前数据传输全部完成. 如果为部分流的话则flags: 0x00.

keep-alive​

  • HTTP协议(七层)的Keep-Alive意图在于连接复用,希望可以短时间内在同一个连接上进行多次请求/响应. 核心在于: 时间要短,速度要快.

  • TCP协议(四层)的KeepAlive机制意图在于保活、心跳,检测连接错误.核心在于：虽然频率低，但是持久.

    当一个TCP连接两端长时间没有数据传输时(通常默认配置是2小时),发送keepalive探针,探测链接是否存活.
