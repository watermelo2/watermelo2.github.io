Spring事务

2025年6月25日 · 阅读需 16 分钟

Spring 默认事务​

有一个事务 A 和 B，如果把 B 放入到 A 里。
问：Spring 开启几个事务？
答：一个事务

追问：如果事务 A 只读，事务 B 更新操作，是否能正常运行？
答：默认情况下能正常运行，当然也能设置不正常运行。

再问：嵌套事务和开启新事务有什么区别？
答：嵌套事务在一般情况（非 JTA 事务）时会添加一个 savepoint，其它东西都不会做修改（主要是 TransactionSynchronizationManager 里的值），而在 JTA 事务情况下会新建事务，但不会调用 suspend() 方法挂起事务，也不保存任何挂起事务资源。

注意：JPA 不支持嵌套事务。

示例配置​

@Bean
public PlatformTransactionManager transactionManager() {
  JpaTransactionManager transactionManager = new JpaTransactionManager();
  transactionManager.setValidateExistingTransaction(true);
  return transactionManager;
}

这样设置会导致不能正常运行。具体看 AbstractPlatformTransactionManager#handleExistingTransaction() 第 475 行。

七种事务传播行为​

传播行为描述
MANDATORY如果当前无事务则抛出异常，否则加入当前事务。
REQUIRED如果当前无事务则开启一个事务，否则加入当前事务。
NESTED如果当前无事务则开启一个事务，否则在一个嵌套的事务中执行。
REQUIRES_NEW如果当前无事务则开启一个事务，否则挂起当前事务并开启新事务。
NEVER如果当前有事务则抛出异常。
SUPPORTS如果当前有事务则加入当前事务。
NOT_SUPPORTED如果当前有事务则挂起当前事务以无事务状态执行方法。

事务涉及到的几个主要类​

名称概念说明
PlatformTransactionManager事务管理器，管理事务的各生命周期方法，下文简称 TxMgr。
TransactionAttribute事务属性，包含隔离级别、传播行为、是否只读等信息，下文简称 TxAttr。
TransactionStatus事务状态，用于表示当前事务的运行状态，下文简称 TxStatus。
TransactionInfo事务信息，内含 TxMgr、TxAttr、TxStatus 以及上一个事务切面的 TransactionInfo（通过 bindToThread() 方法绑定），下文简称 TxInfo。
TransactionSynchronization事务同步回调接口，包含多个钩子方法，如 beforeCommit、afterCompletion 等，下文简称 TxSync 或 transaction synchronization。
TransactionSynchronizationManager事务同步管理器，维护当前线程的事务资源、事务信息以及 TxSync 的集合。

TransactionSynchronizationManager：ThreadLocal 使用最多的类​

核心字段说明：​

  • resources：类型为 Map<Object, Object>，用于保存事务相关资源。
    例如：DataSourceTransactionManager 开启物理事务时会将 <DataSource, ConnectionHolder> 绑定到当前线程，这样业务代码中就能通过 Spring 的 DataSourceUtils 拿到线程绑定的 ConnectionHolder 中的 Connection。

  • synchronizations：类型为 Set<TransactionSynchronization>，用于保存事务同步回调钩子对象，内部含有：

    • beforeCommit
    • afterCommit
    • beforeCompletion

    开发者也可自定义注册，用于追踪事务生命周期。

  • currentTransactionName：当前事务名称。

  • currentTransactionReadOnly：当前事务是否只读。

  • actualTransactionActive：是否存在物理事务。例如传播行为为 NOT_SUPPORTED 时，这个值为 false。

问题与解答​

Q1: TransactionInfo 中的 oldTransactionInfo 是干嘛用的？​

A：配合 ThreadLocal<TransactionInfo> transactionInfoHolder 使用，用于嵌套事务切面时保存上一次事务信息。这样可支持业务代码层手动设置当前事务的回滚等状态。

相关类简介​

  • BeanFactoryAware：实现该接口的类可以获取 BeanFactory 实例。
  • TransactionAspectSupport：封装事务切面处理的核心逻辑，常被 TransactionInterceptor 或 AspectJ 使用。
  • AopUtils：AOP 相关的工具类，常用于获取被代理类的原始类。

关于 txAttr 和 txStatus​

Q2: txAttr 是 CallbackPreferringPlatformTransactionManager 类型代表什么？​

A：

  1. 这个接口与普通事务隔离开，不会影响其它事务；它是 WebSphereUowTransactionManager 中使用的接口，实现了 Spring-TX 的某些机制。
  2. txAttr：代表当前方法声明的事务属性（传播行为、隔离级别等）。 txStatus：当前事务执行状态以及操作控制句柄。
  3. txAttr 的获取方式： 来源于 AbstractFallbackTransactionAttributeSource，Spring 会根据方法或类上的注解去匹配。
  4. TransactionStatus： 封装事务状态，如是否新事务、是否已完成、是否设置为 rollback 等，同时暴露提交、回滚方法。

TransactionAspectSupport#invokeWithinTransaction(...) 调用流程​

1. 获取 TransactionAttribute、PlatformTransactionManager 和连接方法信息
   ↓
2. 调用 createTransactionIfNecessary(tm, txAttr, jp)
   ↓
   - 如果 txAttr 没有名称，则封装为 DelegatingTransactionAttribute，名称为 joinpointIdentification
   - 调用 tm.getTransaction(txAttr) 判断是否需要新建事务，并返回 TransactionStatus
   - 调用 prepareTransactionInfo(...) 构造 TransactionInfo
       ↳ 会保存上一个事务信息（oldTransactionInfo），并绑定当前 txInfo 到 ThreadLocal
   ↓ #begin_try
3. 执行业务逻辑（回调）
   ↓ #catch_throwable
4. 异常处理
   - 如果抛出异常，调用 completeTransactionAfterThrowing(txInfo, ex)
   - 重新抛出异常
   ↓ #finally
5. 最终处理
   - 调用 cleanupTransactionInfo(txInfo) 恢复上一层事务信息
   - 正常返回时提交事务（commitTransactionAfterReturning(txInfo)）

事务挂起 suspend(tx) 的原理​

Q3: ConnectionHolder 和事务、线程的关系是什么？​

A：

  • ConnectionHolder 包含当前数据库连接和事务状态。
  • 事务管理器会将其绑定到 TransactionSynchronizationManager（即当前线程的本地变量中）。
  • 实际事务的提交/回滚操作是通过 ConnectionHolder 或其持有的 Connection 实现的。

Q4: suspend(tx) 是怎么处理事务和线程关系的？​

A：

  • 所谓“挂起事务”：
    • 将当前线程中的事务相关状态信息全部保存到一个 suspendedResources 对象中。
    • 然后清空线程的事务信息，为即将到来的新事务腾出空间。
  • 它和 TransactionSynchronizationManager 密切协作，实现资源保存与恢复。

AbstractPlatformTransactionManager 的三个事务同步方式​

名称概念说明
SYNCHRONIZATION_ALWAYS即使事务结果为空，也会使用事务同步。
SYNCHRONIZATION_ON_ACTUAL_TRANSACTION仅当事务结果不为空时，才启用事务同步。
SYNCHRONIZATION_NEVER永远不会启用事务同步机制。

这些同步策略主要用于控制是否将 TransactionSynchronization 注册到当前事务中，影响如 beforeCommit、afterCompletion 等回调的触发时机与执行。

AbstractPlatformTransactionManager 详解​

基本概念​

AbstractPlatformTransactionManager 是各种事务管理器的抽象基类，封装了事务处理的主流程。子类只需实现以下模板方法：

方法名说明
doGetTransaction()用于从TxMgr中拿一个事务对象，事务对象具体什么类型AbstractPlatformTransactionManager并不care.如果当前已经有事务的话，返回的对象应该是要包含当前事务信息的.
isExistingTransaction()用于判断一个事务对象是否对应于一个已经存在的事务.Spring会根据这个方法的返回值来分类讨论事务该如何传播.
doBegin()物理开启事务.
doSuspend()将当前事务资源挂起.对于我们常用的DataSourceTransactionManager，它的资源就是ConnectionHolder.会将ConnectionHolder与当前线程脱钩并取出来. ConnectionHolder是跟着走的.
doResume()恢复当前事务资源.对于我们常用的DataSourceTransactionManager，它会将ConnectionHolder重新绑定到线程上.
doCommit()物理提交事务.
doRollback()物理回滚事务.
doSetRollbackOnly()给事务标记为回滚.对于我们常用的DataSourceTransactionManager，它的实现是拿出事务对象中的ConnectionHolder打上回滚标记.这个标记是一种“全局的标记”，因为隶属于同一个物理事务，都能读到同一个ConnectionHolder.

AbstractPlatformTransactionManager#newTransactionStatus​

  • suspendedResources：保存上一个被暂停的（调用了 suspend(tx)）资源。

  • newSynchronization：这个参数用于决定是否把事务同步更新到当前线程中。

    答：在 prepareSynchronization 中会通过这个字段来判断是否需要绑定事务到线程；
    同时在 newTransactionStatus() 中也会判断当前线程是否已经绑定了事务。

AbstractPlatformTransactionManager#getTransaction(definition)​

  • 调用 doGetTransaction()

    调用子类重写的方法获取事务对象 tx，如果为空则创建默认的 DefaultTransactionDefinition()。

  • 调用 isExistingTransaction(tx)

    判断是否存在事务。
    如果存在事务，则调用 handleExistingTransaction(definition, tx, debugEnable)。

  • 事务传播行为判断：

    • MANDATORY

      当前无事务则抛出异常。

    • REQUIRED、REQUIRES_NEW、NESTED

      1. 调用 suspend(null)，返回 SuspendedResourcesHolder suspendedResources，暂时挂起当前事务。
      2. #begin_try
        • 声明 newSynchronization，根据当前同步方式判断是否能开启新的同步（传播特性需要创建新的同步）。
        • 调用 newTransactionStatus(definition, tx, newTransaction, newSynchronization, debug, suspendedResources) 创建新的事务状态。

          如果 newSynchronization=true 并且当前线程没有事务，则保持为 true。

        • 调用 doBegin(tx, definition) 开启事务。
        • 调用 prepareSynchronization(status, definition)，如果是新事务则绑定到当前线程。
        • 返回 txStatus。
      3. #catch_RuntimeException_Error
        • 调用 resume(null, suspendedResources) 恢复之前挂起的事务。
        • 抛出异常。

    • SUPPORTS、NOT_SUPPORTED、NEVER

      这几种情况对于当前无事务的逻辑都是直接运行。
      声明 newSynchronization，根据当前同步方式判断是否为 SYNCHRONIZATION_ALWAYS。 因为当前不需要开启新的同步，只有为 SYNCHRONIZATION_ALWAYS 时才为 true。
      调用 prepareTransactionStatus(definition, null, true, newSynchronization, debugEnabled, null)。 该方法等同于 newTransactionStatus() + prepareSynchronization()，注意第二个参数 transaction 为空。

AbstractPlatformTransactionManager#handleExistingTransaction(definition, transaction, debugEnable)​

  • 当前事务传播为 NEVER

    • 抛异常。

  • 当前事务传播为 NOT_SUPPORTED

    • 将当前事务挂起，
    • 返回一个没有事务、不是新事务、需要同步到当前线程、有挂起事务的 TransactionStatus。

  • 当前事务传播为 REQUIRES_NEW

    • 将当前事务挂起。
    • #begin_try
      • 构造一个有新的事务、是新事务、需要同步到当前线程、有挂起线程的 TransactionStatus，
      • 调用 doBegin(tx, definition) 开启新事务，
      • 同步事务属性到当前线程后返回。
    • #catch_RuntimeException
      • 调用 resumeAfterBeginException(transaction, suspendedResources, beginEx) 恢复之前的事务，
      • 抛出异常。
    • #catch_Error
      • 调用 resumeAfterBeginException(transaction, suspendedResources, beginErr)，
      • 抛出错误。

  • 当前事务传播为 NESTED

    • 判断是否需要添加数据库 save_point。（JTA 会覆盖该方法走第二个分支）
    • 如果需要：
      • 构造一个事务不变、有事务、不是新事务、不需要更新线程属性、没有挂起事务的 TransactionStatus，
      • 同步事务属性到当前线程，
      • 调用 status#createAndHoldSavepoint()，
      • 然后返回。
    • 否则：
      • 重新构造一个没有挂起事务的新事务 TransactionStatus，
      • 调用 doBegin(tx, definition) 开启事务，
      • 同步事务属性到当前线程，
      • 返回。

  • 其他情况（到这里还没返回，说明当前需要直接加入上一个事务）：

    • 需要验证：
      • 如果上一个事务不是只读的而当前事务是只读的，说明不能沿用上一个事务，抛出异常。
    • 返回：
      • 调用 prepareTransactionStatus(definition, tx, false, true, debug, null) // 不需要新建事务。

问题与解答​

问：

  1. TransactionSynchronization 是什么？
  2. doSuspend(tx) 主要是做什么操作？

答：

  1. 它相当于一个事务上下文的监听器，包含资源挂起、恢复，以及事务提交前、提交完成、回滚前、回滚完成的通知钩子。
    • 例如，org.springframework.orm.hibernate5.SpringSessionSynchronization 是它的一个实现类，会在 flush() 和 beforeCommit() 方法时调用 Session#flush()。
  2. 将当前事务从当前线程中“挂起”，并返回当前事务及相关事务资源的信息。
    • 所谓“挂起”就是把事务资源从当前线程中取出保存，并清空当前线程的事务属性。

AbstractPlatformTransactionManager#suspend(tx)​

将事务挂起并包装成 SuspendedResourcesHolder

  • 如果当前线程已经激活，则将当前线程中的所有 TransactionSynchronization（即“钩子函数”）全部挂起，并返回挂起的集合。

  • #begin_try

    • 如果传入的 tx 不为空，则调用 doSuspend(tx) 并返回 suspendedResources。
    • 抓取当前线程绑定的事务名、是否只读、隔离级别、是否存在实际事务等信息，并清空这些绑定。
    • 将所有数据包装成 SuspendedResourcesHolder 并返回。

  • #catch_RuntimeException

    • 调用 doResumeSynchronization(susp) 恢复事务同步。
    • 抛出异常。

  • #catch_Error

    • 调用 doResumeSynchronization(susp) 恢复事务同步。
    • 抛出错误。

  • 如果 tx 不为空，则调用 doSuspend(tx)，然后包装成 SuspendedResourcesHolder(susp) 返回。

  • 最后一种情况（tx 为空）则直接返回。

AbstractPlatformTransactionManager#resume(tx, resHolder)​

  • 如果 resHolder 不为空：

    • 取出 suspendedResources，
    • 调用 doResume(tx, suspendedResources) 恢复事务资源，
    • 取出 TransactionSynchronization（“钩子函数”），
    • 如果有， 将之前的信息绑定到当前线程。

  • 调用 doResumeSynchronization(susp)

    • 会调用所有 TransactionSynchronization 的 resume() 方法，
    • 并将这些“钩子”加入到当前线程中。

AbstractPlatformTransactionManager#commit(txStatus)​

  • 如果事务已经完成，则抛出 IllegalTransactionStateException 异常。

  • 如果当前本地事务状态被标识为 rollbackOnly，则调用 processRollback(txStatus) 并返回。

    无论事务如何传播，每次进入事务管理器，在进入业务方法之前都会将一个 TransactionInfo 对象放入 TransactionAspectSupport#transactionInfoHolder。 TransactionInfo 包含一个 TransactionStatus 对象。 commit 方法在业务方法正常完成后调用，所谓当前本地事务状态就是读取当前 TransactionStatus 对象中的 rollbackOnly 标志位。 这是一个局部标志位，只有创建该状态的那一层在业务方法执行完毕后会读取本层状态的该标志位。 用户代码可以通过 TransactionAspectSupport.currentTransactionStatus().setRollbackOnly() 手动将当前事务层的状态标记为回滚。

  • 如果事务被标记为全局回滚，且在全局回滚标记情况下不应提交事务，则调用 processRollback(txStatus) 并返回。

  • 其他情况，则调用 processCommit(txStatus)。

AbstractPlatformTransactionManager#processCommit(txStatus)​

  • #begin_try

    • #begin_try

      • 调用 prepareForCommit(txStatus)

        模板方法，供子类重写。

      • 调用 triggerBeforeCommit(txStatus)

        回调 transaction synchronization 的 beforeCommit 方法。

      • 调用 triggerBeforeCompletion(txStatus)

        回调 transaction synchronization 的 beforeCompletion 方法。

      • 如果当前事务存在 save_point，则释放。

      • 如果当前事务为最外层事务，获取当前事务的 globalRollbackOnly 状态，赋值给局部变量 globalRollbackOnly，然后调用 doCommit(txStatus)。

      • 或者如果调用 isFailEarlyOnGlobalRollbackOnly() 返回 true

        这是一个标志位，如果开启，则会尽早抛出异常。默认是 false。
        这样如果内层事务发生异常，回退到外层事务后会进入该判断。

      • 如果 globalRollbackOnly 为 true，则抛出 UnexpectedRollbackException 异常。

        一般用 DataSourceTransactionManager 不会走到这里，这里是为了兼容 JTA，上面的 save_point 也是。

    • #catch_UnexpectedRollbackException

      • 调用 triggerAfterCompletion(txStatus, TransactionSynchronization.STATUS_ROLLED_BACK)

        回调 transaction synchronization 的 afterCompletion 方法。

      • 抛出异常。

    • #catch_TransactionException

      代表 doCommit 发生异常。

      • 如果配置了 rollbackOnCommitFailure 为 true（默认是 false），则调用 doRollbackOnCommitException(txStatus, ex)。
      • 否则调用 triggerAfterCompletion(txStatus, TransactionSynchronization.STATUS_UNKNOWN)

        回调 transaction synchronization 的 afterCompletion 方法。

      • 抛出异常。

    • #catch_RuntimeException

      • 如果之前没有通知 transaction synchronization，则调用 doRollbackOnCommitException(txStatus, ex)。

    • #catch_Error

      • 如果之前没有通知 transaction synchronization，则调用 doRollbackOnCommitException(txStatus, err)。

    • #begin_try

      • 调用 triggerAfterCommit(txStatus)

        回调 transaction synchronization 的 afterCommit 方法。

    • #finally

      • 调用 triggerAfterCompletion(txStatus, TransactionSynchronization.STATUS_COMMITTED)

        回调 transaction synchronization 的 afterCompletion 方法。

  • #finally

    • 调用 cleanupAfterCompletion(txStatus)

      后续工作：标记 status 为已完成，在最外层清空 transaction synchronization 集合，恢复挂起的事务资源等。

AbstractPlatformTransactionManager#rollback(txStatus)​

  • 如果事务已经完成了，则抛出 IllegalTransactionStateException 异常。
  • 调用 processRollback(txStatus)。

AbstractPlatformTransactionManager#processRollback(txStatus)​

  • #begin_try
    • #begin_try
      • 调用 triggerBeforeCompletion(txStatus);

        回调 transaction synchronization 对象的 beforeCompletion 方法。

      • 如果当前事务存在 save_point 则执行 rollback_save_point;
      • 如果当前事务为外层事务则调用 doRollback(txStatus);

        具体由子类实现。

      • 如果当前存在事务
        • 如果内层事务被标记为 rollBackOnly 或者 globalRollbackOnParticipationFailure 开关开启，则调用 doSetRollbackOnly(status);

          给当前事务标记需要回滚。
          当前事务为内层事务，如果内层事务打上了 rollBackOnly 标记，则整个事务一定回滚，否则 globalRollbackOnParticipationFailure 起作用。
          它默认开启，即内层事务失败，最终结果是全事务回滚。若关闭该开关，外层事务业务方法可根据情况决定是否回滚。

    • #catch_RuntimeException
      • 调用 triggerAfterCompletion(txStatus, TransactionSynchronization.STATUS_UNKNOWN);
      • 抛出异常 ex。
    • #catch_Error
      • 调用 triggerAfterCompletion(txStatus, TransactionSynchronization.STATUS_UNKNOWN);
      • 抛出错误 err。
    • 调用 triggerAfterCompletion(txStatus, TransactionSynchronization.STATUS_ROLLED_BACK);

      回调 transaction synchronization 对象的 afterCompletion 方法。

  • #finally
    • 调用 cleanupAfterCompletion(txStatus);

      后续工作：状态标记为 completed，清空事务同步集合，恢复挂起的事务资源等。

关键方法说明​

  • AbstractPlatformTransactionManager#doGetTransaction()
    模板方法，用于从事务管理器中获取一个事务对象，具体类型由子类决定。如果当前已有事务，则返回包含当前事务信息的对象。

  • AbstractPlatformTransactionManager#isExistingTransaction()
    用于判断事务对象是否对应已有事务。Spring根据该方法返回值判断事务传播行为。

  • AbstractPlatformTransactionManager#doSetRollbackOnly()
    给事务标记为回滚。以常用的DataSourceTransactionManager为例，具体实现是从事务对象中取出ConnectionHolder并设置回滚标记。
    这个标记是“全局”的，同一物理事务中的所有参与者都能读取到。

  • DefaultTransactionStatus#isNewSynchronization()

    在AbstractPlatformTransactionManager#prepareSynchronization(txStatus, definition)方法中，如果需要同步事务状态到当前线程，会把definition中的isReadOnly属性同步进去。

NESTED事务与NEW事务的区别（事务实现分一般情况事务和JTA事务）​

一般情况​

  1. NEW事务
    会将当前线程挂起，然后自己开启一个新事务，默认情况下会把当前事务属性保存到线程中。提交或回滚事务时，恢复之前的事务属性。

  2. NESTED事务
    不会干预当前事务的任何属性，只是添加一个 savepoint（保存点），当前线程的状态不做任何修改。

  3. 提交事务时
    会首先判断当前事务是否含有 savepoint：

    • 如果有，则执行两步操作：获取当前事务的 rollback 属性值；释放 savepoint。

  4. 回滚事务时
    会首先判断当前事务是否含有 savepoint：

    • 如果有，则调用 DefaultTransactionStatus#rollbackToHeldSavepoint()；
    • 该方法会对 savepoint 进行回滚操作，并释放当前线程状态相关的 savepoint 资源。

另外JPA 不支持嵌套事务（savepoint）

JTA事务​

  1. 嵌套事务不会将当前事务挂起，也不会挂起当前线程的 readOnly 等属性。

  2. 其它细节未确定，不清楚后续是否会恢复相关属性。

问：Spring事务失效排查方向有哪些？​

  • @Transactional 注解应用在非 public 修饰的方法上，导致失效。
    参考：AbstractFallbackTransactionAttributeSource#computeTransactionAttribute。

  • @Transactional 注解属性 propagation 设置错误。

  • @Transactional 注解属性 rollbackFor 设置错误。

  • 同一个类内部方法调用，导致 @Transactional 失效。

  • 异常被 catch 吃掉，导致 @Transactional 失效（这是经验较少者常见的排查盲点）。

  • 数据库引擎不支持事务。

  • Spring MVC 扫描的是父容器定义的 Service，而动态代理只定义到 Root 容器。

  • 目标对象没有被 Spring 容器管理。

  • 分布式事务问题。
